# Device: CH57x knob `514c:8850`

The device this tool was built for: a small **Bluetooth rotary encoder with a push
button** (knob-only — no separate keys). It's sold under several brand names; the
identity that matters is the USB VID/PID pair below.

## Identity

| Property   | Value                                    |
| ---------- | ---------------------------------------- |
| USB VID    | `0x514c` (20812)                         |
| USB PID    | `0x8850` (34896)                         |
| Chip family| WCH CH57x                                |
| Connects   | USB **and** Bluetooth LE                 |

It enumerates over both transports. **Programming must be done over USB** — the
config channel is only reachable on the wired interface.

## HID interfaces (`knobctl probe`)

```
iface #0  usage_page=0xff00 usage=0x01   <- config channel (program here)
iface #1  usage_page=0x0001 usage=0x06      keyboard output
iface #1  usage_page=0x0001 usage=0x02      mouse output
iface #1  usage_page=0x0001 usage=0x01      pointer
iface #1  usage_page=0x000c usage=0x01      consumer / media output
```

The knob's rotation/press produce input on the keyboard / mouse / consumer
interfaces; the mapping that decides *which* is stored in firmware and pushed over
the `0xff00` interface. The keyboard interface uses **numbered reports** (report id in
byte 0), which is why `knobctl watch` decodes report id → payload.

## Knob actions (confirmed)

The `key_id` for the single knob (index 0) is **confirmed by actuation**:

| Action | key_id |
| ------ | ------ |
| ccw    | 16 (0x10) |
| press  | 17 (0x11) |
| cw     | 18 (0x12) |

Key ids `1..15` are **phantom keyboard defaults** (a, b, c…) — firmware has 16 button
slots even though this unit has no physical keys.

## Combo slots (ids 19–24)

The firmware treats **press-held rotation as a "virtual knob 1"** (key_id
`16 + 3·1 + action`):

| Gesture   | key_id | `set` target | Confidence |
| --------- | ------ | ------------ | ---------- |
| press+ccw | 19     | `press+ccw`  | confirmed (set by name in vendor app) |
| press+press (double?) | 20 | `press+press` | **phantom — never emitted** (tested: double-click fires `press` id 17 twice, not slot 20) |
| press+cw  | 21     | `press+cw`   | confirmed |

`knobctl read` names ids 19/20/21 accordingly, and `set` accepts `press+ccw` /
`press+cw` / `press+press` (equivalently `knob1.ccw` etc.).

Ids `22..24` (0x16..0x18) are a further group ("virtual knob 2") whose physical
gesture isn't identified. Slot 20 is now confirmed phantom (see above); to pin down
22–24, run `knobctl watch`, perform each gesture, and match the emitted report to a
`set` on the candidate id.

There is no long-press or double-press event on this hardware: press duration is not
tracked, and a double-click emits two plain `press` (id 17) events. Tap-vs-hold /
double-click behavior has to be implemented host-side (e.g. Karabiner/Hammerspoon).

## Layers

The device stores **3 independent layers** (`knobctl read` dumps all three; `set
--layer N` targets one). Only one layer is active at a time, and the knob operates on
**layer 0** by default. Layers 1 and 2 hold the factory media defaults out of the box.

> **Open item:** how (or whether) the active layer is switched at runtime on this
> knob-only unit is not captured. If the vendor app can switch layers, capture that
> command (see [`protocol.md`](./protocol.md#reverse-engineering)) to add it to knobctl.

## Global settings

- **RGB backlight** — effect modes 0..5, set via `knobctl rgb <mode>`. Write-only.
  Confirmed visually on this unit (modes 0..5 each produce a distinct effect; 6 does
  nothing). The firmware accepts the command regardless of whether a given unit
  actually has LEDs, so on a non-backlit variant it's a silent no-op.
- **Mouse report latency** — milliseconds, set via `knobctl latency <ms>`. Write-only.

See [`reading-the-current-mapping.md`](./reading-the-current-mapping.md) for what can
and can't be read back.
